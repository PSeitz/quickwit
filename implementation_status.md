# ingesthree: implementation status

## Current status

**Local storage, write-queue admission and validation, automatic file finishing, the active-writer limit, file registration, upload/register/local-delete handoff, startup recovery before intake, and full handoff drain are implemented. Metastore assignment and atomic split publication/input completion are also implemented. An opt-in service path now connects intake/routing, supervised indexing, and shutdown. Ingesthree requires standalone compaction on separate compactor nodes, using the existing planner's metastore discovery. Janitor deletes completed input objects while retaining completion evidence. Cleanup of objects without completed records and production resource/rollout safeguards remain pending. Handoff verification includes stalled HTTP uploads, S3 emulation with a persistent metastore, and five process-kill windows. Live AWS operation remains unverified.**

The goal is to remove complexity that has caused incidents. Other benefits are secondary. Decisions and their rationale are recorded in [design_answers.md](design_answers.md). This document tracks agreed behavior separately from proposals and unresolved implementation choices.

## Agreed data flow

```text
HTTP ingest → reused router forwards documents to an eligible ingester
own node with positive capacity → same-AZ two-choice peers → capacity, then affinity

Ingester, per index:
reserve write-queue space + local storage → configurable validation → append locally
→ flush to kernel → acknowledge clients through the router
acknowledged data survives process/container crashes while host and storage remain available
size threshold or fixed timeout → finish file and start a new one
finished file → upload to S3 → register available file in metastore

Independent indexing pipeline, one task with no stage actors:
self-assign eligible same-index files in metastore, oldest first → read from S3
→ process and index whole files in RAM → finalize splits to disk + package
→ upload all output splits
→ atomically publish outputs and complete all contributing files, first publication wins

Standalone compaction:
planner discovers published splits in metastore → separate compactor nodes merge them

Input cleanup after completion: Janitor periodically deletes completed inputs from S3
```

All ingest clients, including external producers, receive acknowledgment after flush to the kernel. Acknowledged data must survive process/container crashes while the host and storage remain available. Host-crash durability/fsync and pod-replacement storage remain open. S3 plus metastore registration provides the handoff to indexing. Input deletion follows successful atomic publication and file completion. Janitor retries completed-input deletion on later GC passes. Cleanup without retained completed records remains separate work.

### File assignment and publication

The concept is **file assignment**, implemented by `AssignFilesForIndexing`.

1. The metastore selects the oldest eligible file, then a same-index prefix subject to file-count and byte targets. Ready files and unfinished files whose processing start is strictly older than the requested retry delay are eligible. Registration Unix seconds and file ID define ordering. The oldest file is included even when it alone exceeds the byte target.
2. Selection and recording processing start are atomic. Assignment carries no owner or publication lease. A lost response leaves the work recoverable after the retry threshold.
3. The future pipeline task processes whole files together, serializes/packages their outputs, and uploads them. Crossing the retry threshold permits another attempt to start, possibly with an overlapping group.
4. **The first publication transaction to commit wins.** `PublishFileSplits` atomically publishes the full output set and completes all contributing files, regardless of latest assignment. An input completed by another publication rejects the whole group. After success, the standalone compaction planner discovers outputs through its metastore scan.
5. Each attempt retains a unique publication ID and immutable input/output sets across retries. Completion evidence identifies the winning attempt even after output splits are removed. Losing attempts must clean only their own outputs. Worker cleanup remains unimplemented.

Assignment limits duplicate work. It grants no exclusive publication right. An earlier, slow attempt remains allowed to win after reassignment. Assignment renewal and publication fencing by assignment identity are unnecessary for this design.

The metastore stores state and checks conditional updates. Pipelines initiate assignment. Any pipeline can recover unfinished work through the same eligible-file discovery. Correctness requires neither rendezvous hashing, placement on the original pipeline, node-level assignment bookkeeping, nor a local assignment journal. A separate recovery process is optional.

## Completed inspection

These findings describe existing code, rather than implemented ingesthree behavior. Details and inspected paths are in [design_answers.md](design_answers.md).

- Ingest replication has already been removed in this checkout. The replication-factor setting is ignored.
- Every node instantiates a router. Indexer nodes also run an ingester. The router forwards document payloads in persist calls, with an in-process call when it selects itself. Current selection prefers the same AZ and higher WAL free-capacity score, with no extra self preference.
- Existing `QW_ENABLE_IN_MEMORY_INDEXING` builds in a RAM directory, then persists finalized splits to disk for packaging/upload. This is the selected storage approach for the proposed indexing pipeline.
- The pinned `mrecordlog` revision (`3b3562ef`) multiplexes logical queues into shared physical WAL files. Producing single-index upload files would require extraction.
- `mrecordlog` retains untruncated records in application memory and uses buffered I/O. Its recovery loop skips some corrupted records. Interrupted-write handling needs validation before adoption.
- Current ingest-v2 uses a five-second delayed `Flush` policy, checked during log operations rather than by an independent flush timer. It can acknowledge before userspace-buffered data reaches the kernel. This remains the existing-implementation baseline. The proposed design requires flush before acknowledgment. See the crash-scope discussion in [design_answers.md](design_answers.md#flush-fsync-and-pod-crashes).
- Mapping changes replace affected pipelines. Current indexing logs, counts, and skips invalid documents while advancing source progress. This finding leaves the new mapping/configuration policy open.
- Direct I/O bypasses the data page cache but still needs durability and interrupted-write handling. Alignment and final partial blocks need treatment. Buffered upload reads would populate the page cache again.

## Implemented local core

`quickwit/quickwit-ingest/src/ingesthree/` contains a synchronous, single-owner core with per-index-incarnation files, flush-before-success, manual file finishing, restart recovery, and a logical input-byte budget including framing. It defaults to `<data_dir>/ingesthree`. The service path is opt-in through `ingest_api.enable_ingesthree`. Full details and the experimental format are in its [README](quickwit/quickwit-ingest/src/ingesthree/README.md).

`WriteQueue` queues document batches for validation and writing through that core. Clones share queue and disk byte limits and reserve both together. It reuses JSON/schema validation with per-document errors and drains queued writes before stopping. Validation runs on the CPU pool and IO on the blocking pool. Disk reservations settle to file growth, and disk usage includes recovered files. The queue budget covers queued and processing input buffers and descriptors. Validator scratch and response allocations are separate.

The core finishes files at the size target and rejects additional writers at the active-file limit without stopping the worker or finishing existing files. The writer loop finishes files at fixed creation deadlines, prioritizing expiry over queued requests. A batch already being validated or written can finish in its current file after expiry. The loop finishes expired files before taking the next request. Finishing preserves retained disk charges and stops on IO failure.

An optional `Uploader` connects the writer to storage and metastore registration. It streams finished files unchanged to `<configured-prefix>/<file_id>`, registers them, and lets the writer delete local copies before releasing both disk charges. The writer polls upload/registration alongside deadlines and incoming batches. Retryable failures wait one second. Known upload success skips subsequent uploads, and known registration success leaves only deletion to retry. Missing-index registration logs an error, deletes the uploaded object and local file, releases disk capacity, and continues. Remote deletion retries every second, treating an absent object as deleted. Other permanent registration failures stop intake and retain accepted local data. Upload authorization/missing-resource failures also stop immediately. Other storage error categories can include transient failures and retry. One file is processed at a time, so transient failures hold up later files. The upload destination must stay unchanged while local files remain.

`WriteQueue::open` with an uploader completes upload, registration, and local deletion for each recovered file before exposing intake. Recovery processes one file at a time and releases its disk charge after deletion. Registration or deletion delays block subsequent recovery files and intake. The normal writer starts after recovery with fresh files. No recovered-ID set or deferred-registration queue is carried into it. `Uploader` holds only storage and metastore clients. `finish()` cancels handoff and finishes files locally. `drain()` stops admission across clones, completes queued writes, finishes active files, and waits for upload, registration, and local deletion before releasing ownership and replying. Cancellation retains remaining files, releases ownership after local work finishes, and leaves intake closed. The directory stays locked until both local writers and handoff are dropped, including local IO failure paths.

The header guard, separate router/RPC discovery, indexing-service startup, and worker supervision are implemented behind `ingest_api.enable_ingesthree: true`. Physical allocation/inode overhead, free-space checks, and recovery/drain reserves still need admission integration. Restart replays retained files under their original IDs. Cleanup after index deletion following successful registration remains unresolved. Janitor catches late uploads after remote cleanup while completion evidence remains. Missing-index registration already discards obsolete inputs during normal handoff, startup, and drain. Replaying a completed file can recreate a remotely cleaned object.

## Implemented metastore registration

`RegisterFileForIndexing` stores a `DocumentsStagedForUpload` record with the index incarnation, canonical file ULID, storage URI, byte size, and registration time in PostgreSQL and the file-backed metastore. Repeated registration returns the existing record unchanged, including registration, processing, and completion timestamps. The caller keeps index UID, URI, and size unchanged across retries. Registration uses the stored metadata without comparing it with the request. Missing or deleted index incarnations fail. Migration `30_create-staged-files` adds the PostgreSQL table with `file_id` as its sole primary key and `index_uid` as a required foreign key. PostgreSQL enforces file ID uniqueness across indexes. The file-backed metastore keeps per-index maps and relies on callers to generate globally unique IDs. See the [API and storage contract](quickwit/quickwit-metastore/README.md#ingesthree-file-registration-for-indexing).

The ingester calls this API after confirmed upload when an `Uploader` is configured. `AssignFilesForIndexing` and `PublishFileSplits` now implement assignment and atomic publication/completion in both backends and through gRPC. Migration 31 adds winner IDs, partial assignment indexes, and whole-second registration ordering. File-backed persistence finishes and reconciles its cache after caller cancellation, including other whole-index mutations that could otherwise overwrite completion evidence. Its global assignment scan excludes concurrent mutations. See the [API contracts](quickwit/quickwit-metastore/README.md#ingesthree-assignment-and-publication). Worker service integration and Janitor completed-input deletion are implemented. `ListCompletedFiles` provides read-only keyset pagination in both backends. Migration 32 adds a partial index for completed-file listing. Completion-evidence expiry remains pending.

## Implemented file indexing

`quickwit-indexing/src/ingesthree/S3Indexer::index_next` claims a group, reads its staged files, converts documents, builds/serializes/packages/uploads splits, and atomically publishes them with input completion. It reuses the v2 operations through actor-independent functions. No stage actors or channels were added. Mapping, routing/overflow, clustering, timestamps, delete-opstamp metadata, merge maturity, split format, and the node-wide upload semaphore are preserved. Invalid documents are counted/logged and skipped. Corruption fails the group, including after earlier outputs have uploaded. Publication retries retain the same input/output sets and publication ID.

Service startup runs `quickwit_common::num_cpus()` workers per indexer node (`QW_NUM_CPUS`), each with idle polling and independent failure/panic restart backoff. Shutdown cancels and joins all workers. The worker ends at durable publication. The existing standalone compaction planner scans published immature splits and assigns merges to separate compactors, including after planner restart with the publishing indexer stopped. Ingesthree indexers require standalone mode. The planner waits for all live indexers, including v2 members, to advertise that mode. Indexer-local merge ownership, notifications, reconciliation, and configuration restarts have been removed. Output-schema-based tag extraction keeps older mappings safe. Shutdown stops worker restarts and drains intake. Unexpected writer closure fails the server for process-level recovery. Blocking indexing work retains its scratch root after caller cancellation. Janitor deletes completed input objects. Abandoned outputs remain for separate cleanup. The 1,000-output publication ceiling requires compatible group/indexing limits or an explicit handling policy, including inputs that individually exceed it. Memory/disk admission and performance validation remain rollout prerequisites. See [worker behavior and limits](quickwit/quickwit-indexing/src/ingesthree/README.md).
